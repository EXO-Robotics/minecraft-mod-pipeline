# AI agent operating model

The agent should treat the toolkit as a constrained evidence and build environment, not as a `convert` button.

1. Open the revisioned project and inspect status, blockers, unresolved decisions, and next task.
2. Scan each mod and inventory registrations, content, assets, dependencies, mixins, packets, GUIs, and unsupported constructs.
3. Query focused evidence and source/JAR parity instead of inferring missing behavior.
4. Extract behavior intent and ask a human to resolve material ambiguity.
5. Compare direct, stable-script, native redesign, original replacement, defer, and unsupported strategies.
6. Record an accepted plan with evidence, risks, fidelity, and target-profile constraints.
7. Generate deterministic packs and scaffolds.
8. Put non-generic behavior in protected custom handlers with provenance; never silently replace it on regeneration.
9. Run schema, API, static, assets, performance, rights, packaging, Creator Tools, and runtime checks.
10. Diagnose receipts against expected behavior, repair the smallest evidence-backed layer, and retest.
11. Record approximation decisions, residual risk, physical-test requirements, and final fidelity.

## Example: special weapon

The agent inspects item registration, use callbacks, projectile/effect calls, cooldown state, recipe, texture, and sound. It can generate item/recipe/projectile scaffolds and select the projectile or cooldown pattern. The agent must decide whether the Java animation/keybinding can become normal use/use-on-block, implement protected impact behavior, then verify static APIs, direct effect invocation, collision adapters, cooldown isolation, and a physical player firing it. Missing renderer parity becomes an approved native visual redesign, not a hidden omission.

## Example: custom boss

The agent inventories entity registration, attributes, drops, spawn path, phase thresholds, minions, arena rules, and client rendering. It maps supported lifecycle/hit/hurt/death evidence into a Bedrock entity plus a scripted state machine, records unsupported Java AI/rendering, and proposes an original Bedrock-native phase design. Tests cover deterministic transitions, restart state, drops, and BDS adapters; physical-client combat, two-player targeting, controller readability, and console load remain required.

## Example: persistent machine

The agent traces block interaction, inventory/recipe logic, tick scheduling, location identity, ownership, and save format. It reuses DoorLock canonical location/revisioned migration patterns and Clockwork machine processing/form patterns, chooses a batched scheduler, and estimates console cost. It then tests canonicalization, ownership, interruption recovery, restart progress, chunk unload/reload, two-player contention, cleanup on break, and physical controller interaction. Global per-tick Java simulation is rejected or redesigned when it cannot fit the budget.
