# Run a Java-to-Bedrock campaign

Act as the campaign controller. Route specialist work to the existing skills
instead of repeating their instructions.

Read [campaign-state-machine.md](references/campaign-state-machine.md) before
creating lanes, assignment packets, or a final classification.

## Route the work

- Use `$translate-java-mods-to-bedrock` for the governing standards, role
  contract validator, clean-room boundary, feature mappings, and gate ledger.
- Use `$analyze-java-mod-evidence` for the evidence-only inventory and feature
  graph.
- Use `$sanitize-java-bedrock-contracts` for the one-way
  `observation → abstract requirement → product selection` transfer.
- Use `$produce-bedrock-cleanroom-feature` and
  `$integrate-bedrock-subsystem` for evidence-blind implementation and
  dependency-wave integration.
- Use `$blockbench-build-bedrock-assets` for original editable assets, native
  exports, proof views, and Golden gates.
- Use `$launch-cleanroom-production-worker` before any isolated production or
  repair worker starts.
- Assign `$qualify-bedrock-candidate` as the read-only BDS qualification role.
  Its execution harness uses `$qualify-bedrock-addon-bds` for MCTools,
  immutable package binding, architecture controls, Stable/Preview runs, and
  exact receipts.
- Assign `$audit-java-bedrock-cleanroom`,
  `$audit-golden-blockbench-asset`, and
  `$audit-bedrock-portfolio-freeze` only after candidate freeze.
- Use `$freeze-bedrock-campaign-bundle` for the final slim bundle and manifest.
- Use `$crazycraft-quarter-distillation` only when the user requests scope
  reduction. Do not quarter-distill a specifically named full-mod campaign.

## Establish the campaign

1. Resolve the repository, branch, dirty state, storage, installed tools, and
   approved output roots.
2. Freeze one target mod or connected subsystem. Do not let a modpack campaign
   silently expand to unrelated mods.
3. Acquire from the user-approved official endpoint before using a fallback.
4. Reject HTML, JSON, truncated, corrupt, path-traversing, or unrelated
   downloads. Never execute launchers, scripts, installers, native binaries, or
   JARs during acquisition.
5. Hash the archive, exact bundled artifact, dependencies, configs, and
   comparison artifact separately. The bundled version remains authority when
   it differs from a standalone release.
6. Create physically distinct `evidence`, `control`, `production`, `audit`, and
   `qualification` lanes. Keep raw Java expression out of production.
7. Read the repository's role-contract standard and validate every assignment
   before launch. Reject a role or gate result that lacks exact hashes, lane
   boundaries, authority, stop states, or receipt policy.

## Control parallel work

Use one controller and bounded section leads. Give every task owner:

- Lane and writable-path ownership.
- Exact input hashes and expected output paths.
- Allowed and denied materials.
- Stop conditions and required receipt.
- A warning that other workers exist and their work must not be reverted.

Keep evidence workers read-only toward production. Give production workers only
sanitized contracts and opaque requirement IDs. Give private semantic oracles
to independent auditors only after candidate freeze.

For every promoted feature, record all three states separately:

- `ARTIFACT_PRESENT`
- `SERVER_LOADABLE`
- `PLAYER_REACHABLE_FEATURE`

Only the last state proves a normal survival acquisition or spawn path reaches
the interaction, event handling, reward, and persistent result. Test-only
summons and unobtainable recipe inputs do not satisfy it.

Do not run more hero-asset builds concurrently than the machine and visual
review budget can support. Prefer two concurrent hero assets unless the
campaign explicitly freezes another bound.

## Advance gates

Advance only through:

`TARGET_FROZEN → INVENTORY_COMPLETE → CLEAN_ROOM_CONTRACTED →`
`PRODUCTION_ACTIVE → STATIC_QUALIFIED → GOLDEN_QUALIFIED →`
`INTEGRATED → AUDITED → BDS_QUALIFIED → BUNDLE_FROZEN`

At each gate:

- Record exact commit, tree, artifact hash, receipt hash, passed claims,
  failed claims, and untested claims.
- Keep the working tree and package immutable while a gate runs.
- Preserve failed and superseded candidates.
- Return only abstract repair findings across the clean-room boundary.

## Repair honestly

Use `record → diagnose → material repair → freeze replacement → rerun
invalidated gates`.

Never retry unchanged bytes until a desired streak appears. An unchanged
candidate failure closes that bounded ledger. Run diagnostic controls under a
different label, make a material change, then begin a fresh declared ledger.

Do not blame a pack before running bounded controls such as packless,
manifest-only, BP-only, RP-only, and architecture-matched execution. Preserve
every declared run, including teardown anomalies and silent pre-start exits.

Stop only at the campaign's authorized hard blockers or bounded repair limit.
Do not stop after download, inventory, contract generation, first asset pass,
or first repairable BDS failure.

## Finish narrowly

Require:

- Exact bundled artifact and target freeze.
- Complete feature disposition matrix with zero unclassified entries.
- Clean-room production and repair receipts.
- Deterministic package bytes.
- MCTools zero errors.
- Golden thresholds and independent visual audit.
- Independent runtime, contamination, lineage, and isolation audits.
- Commit-bound Stable and Preview BDS receipts.
- Player-reachability records for every promoted feature.
- A passing independent portfolio-freeze audit.
- A slim final bundle with all-file manifest.

Always keep desktop rendering, controller gameplay, real multiplayer reconnect,
Realm, split-screen, physical PS4, Marketplace, and release statuses explicit.
BDS qualification does not prove them.
