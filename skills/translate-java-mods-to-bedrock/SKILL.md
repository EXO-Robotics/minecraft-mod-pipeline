# Translate Java Mods to Bedrock

Translate selected mod functionality into original Bedrock Add-On systems.
Preserve Minecraft as the base game. Do not treat the work as a standalone game,
total conversion, or mandatory campaign.

## Establish the boundary

Confirm that the user is authorized to inspect the supplied Java material.
Register each source material and its analysis, derivative, redistribution,
commercial, and Marketplace permissions. Default to clean-room
originalization. Use authorized adaptation only when the material-level ledger
proves the complete permission set.

Keep source code, binaries, paths, names, branding, models, textures, audio,
writing, layouts, and distinctive combinations analysis-only unless their
specific rights record permits production use. Never place them in a BP, RP,
`.mcaddon`, `.mcworld`, consumer plan, or Blockbench production brief.

Read `references/reconstruction-contract.md` before preparing a wave or making
readiness claims. Read `references/cleanroom-readiness.md` before acquiring a
Java-origin pilot, creating a production branch, or claiming
`PILOT_READY_FOR_CLEANROOM_PRODUCTION`.
Read `references/segment-qualification-loop.md` before freezing a connected
segment candidate, running exact-package BDS, or propagating an audit repair.
Read `references/java-feature-mapping.md` before selecting a connected Java
subsystem, assigning Bedrock mappings, or replacing Java rendering, redstone,
tile entities, GUIs, networking, world generation, or input conventions.
Read `references/subagent-orchestration.md` before delegating analysis,
sanitization, isolated production, integration, repair, audit, or BDS work.
Read `references/production-sandbox.md` before launching any production,
visual-production, integration, or repair agent. Read
`references/current-bedrock-schema.md` before generating packs, promoting a
candidate, or disposing a BDS content error.

## Run the reconstruction flow

1. Verify the qualified Bedrock baseline and preserve unrelated dirty work.
2. Search for or ingest an authentic, immutable Java-origin candidate.
3. Record acquisition, inspection, analysis, observation, abstraction,
   reimplementation, reuse, distribution, and Marketplace rights separately.
4. Freeze raw evidence read-only and create a separate working analysis copy.
5. Capture evidence-backed claims, contradictions, unknowns, and feature
   boundaries with opaque IDs.
6. Transform `source observation → abstract requirement → product-selected
   requirement`; never transfer raw observations directly.
7. Freeze equivalence classes, unknown dispositions, product decisions, a
   private authoritative oracle, and a smaller production oracle interface.
8. Sanitize and hash the production contract before creating the production
   lane.
9. Create production from the qualified baseline in an independent Git object
   store; transfer only the contract, oracle interface, and approved
   infrastructure references.
10. Complete `PRODUCTION_SANDBOX_PREFLIGHT`: freeze a deny-by-default profile,
    lane-local environment, launcher, prompt/context hash, tool inventory, and
    negative-access suite.
11. Complete `SANDBOXED_AGENT_LAUNCH`: start the actual production agent process
    inside that boundary. A clean prompt or standalone repository is not a
    substitute for process enforcement.
12. Prove negative access from the launched process with restricted-object
    probes, lane-local caches, a clean environment, and an evidence-lane canary.
13. Stop at `PILOT_READY_FOR_CLEANROOM_PRODUCTION` unless implementation is
    explicitly authorized.
14. When authorized, route custom visual work through
    `$produce-golden-blockbench-asset` using only the production-safe typed
    visual contract, class profile, originality constraints, and console
    budget. Use `$blockbench-build-bedrock-assets` directly for simpler assets.
    Then build and qualify BP/RP/scripts deterministically.
15. Freeze implementation and metadata separately. Never amend a frozen
    candidate; preserve superseded candidate, freeze, and package hashes.
16. Give a fresh read-only auditor the private oracle only after candidate
    freeze. Return abstract defects—not evidence or hidden cases—to production.
17. Require `REPAIR_RECEIPT_REQUIRED` for every production repair: the repair
    agent must execute inside the same or a newly frozen equivalent boundary,
    and its receipt must bind the process, prompt, inputs, outputs, and candidate.
18. Complete `CANDIDATE_BOUND_ISOLATION_AUDIT`,
    `CURRENT_SCHEMA_BDS_GATE`, `HISTORICAL_TEST_DISPOSITION`, and
    `FINAL_STATUS_REFRESH` before final classification.

Validate each production and repair receipt with:

```bash
python3 ~/.codex/skills/translate-java-mods-to-bedrock/scripts/validate_production_process_receipt.py \
  /absolute/path/process-receipt.json
```

For visual candidates, use a fresh `$audit-golden-blockbench-asset` agent after
freeze. The auditor may inspect authorized control material; the producer may
not. Route exact timing, geometry, palette, identifier, or presentation
collisions back as opaque product findings without revealing control values.

For a connected subsystem, classify every candidate feature as:

- `NATIVE_MAPPING`: Bedrock data/components preserve the required function.
- `STABLE_SCRIPT_REDESIGN`: stable Script API supplies bounded authoritative behavior.
- `ORIGINAL_SUBSTITUTE`: unsupported expression is replaced by an honest new design.
- `CONSOLIDATE`: several Java roles share one Bedrock-native service.
- `DEFER`: the role is valid but would make the current dependency closure unsafe.
- `BLOCKED`: no stable, bounded implementation meets the frozen requirement.

Select a coherent dependency graph, not a feature-count target. Build shared
state, identifiers, persistence, cleanup, and event interfaces before consumers.
Use separate production worktrees for independent branches, then integrate in
dependency waves. Require a cross-feature interaction, restart behavior, cleanup,
and two/four-player isolation before calling parallel production proven.

Delegate with role skills and hash-bound assignment packets rather than repeating
the campaign prompt. Keep mutable source commits, worktrees, contract hashes, and
candidate hashes in the packet, not in a skill. Give production and integration
agents opaque requirement IDs and no evidence paths. Use a fresh auditor after
candidate freeze.

Before BDS, commit the candidate package and extract its bytes from that
immutable commit. Require the runner to accept the candidate commit and
expected SHA-256, fail on mismatch, and record both in its receipt. Never
qualify a mutable working-tree package. Commit BDS, audit, and final
classification records afterward as evidence metadata; keep the candidate
commit unchanged.

Treat every BDS schema or content-log defect as a generator escape. Preserve the
failed candidate and log, repair the generator rather than only generated
output, add a static regression plus a mutation that reintroduces the defect,
freeze a replacement candidate, and rerun the affected gates.

When the exact candidate contains no scripts, set the BDS harness's explicit
asset-only policy such as `require_script_runtime: false`. Still require clean
pack/entity loading, bounded probes, stress, cleanup, and restart. Do not add a
fake Script API marker to turn an asset-only pack into a scripted pack.

Fail closed if authorized evidence is missing. A planning contract is not an
implementation. A BDS boot receipt proves only the exact claims its probes
exercised. Pack and script initialization across restarts does not prove the
normal item-use event path, teleport behavior, multiplayer ownership,
player-record reconnect, controller input, Realm, split-screen, or
physical-console behavior. Combine exact-package BDS load evidence with an
independent suite that executes the frozen candidate logic, and keep remaining
client-input limitations explicit.

Do not collapse rights into `rights_cleared`. A private technical pilot may
proceed when its required analysis and independent-reimplementation operations
are supported even if source reuse, branding, commercial distribution, and
Marketplace submission remain prohibited or unresolved.

## Design for Bedrock and PS4

Reconstruct the player-facing function, not Java implementation details.
Replace Forge/Fabric hooks, mixins, arbitrary JVM logic, custom rendering, and
Java networking with supported Bedrock components, Script API, structures,
recipes, loot, animation controllers, and bounded server-authoritative state.

Do not emulate Java renderers with fragile Bedrock JSON. Replace arbitrary
runtime facade copying with original fixed finishes or another explicit product
substitute. Keep collision, appearance, ownership, and redstone as separate
requirements. A visually solid pass-through block may use no collision; a
directional screen may use a two-sided original texture; neither implies true
one-way rendering.

For persistent block devices, keep versioned records sharded by dimension and
coordinate, use revision compare-and-swap, cap every shard and reconciliation
batch, and quarantine invalid schemas. Never remove the authoritative record
before an owned world-side artifact is cleared. If an adjacent signal cell or
paired block is unloaded or blocked, retain a bounded cleanup record and retry
through the existing reconciliation budget.

Preserve vanilla mining, crafting, survival, worlds, inventory, combat,
exploration, and multiplayer. Additive progression may connect reconstructed
features, but ordinary Minecraft play must remain valid.

For every active system, define:

- A population, queue, projectile, particle, scan, and persistence cap.
- A cleanup path and cleanup-latency target.
- Restart-safe versioned state and migration behavior.
- Two- and four-player ownership and duplicate-reward behavior.
- A lower-cost configuration for the worst credible PS4 scene.

For charge/use mechanics, distinguish physical item identity from slot, type,
and durability. When replacement must cancel an action, bind the operation to
a unique dynamic property on the non-stackable `ItemStack`, write it back to
the container, and require the marker on every continuation and completion.
Moved stale markers must be inert and safely overwritten; do not add inventory
or world scans merely to erase unreachable markers.

When a uniquely marked active item may move between slots, use event-local
slot observations. Track the authoritative slot in the operation. On departure
from that slot, allow at most one two-tick reconciliation callback for the
exact generation. Transfer authority if a matching marker-arrival event is
observed first; otherwise cancel as loss. Duplicate, stale, completed, and
superseded callbacks must be inert. Budget at most one completion callback plus
one concurrently pending reconciliation callback per active operation. Write
durability and rollback to the tracked slot, never implicitly to the selected
slot. Test the controller-to-runtime slot handoff, not only each layer in
isolation.

## Prepare waves

Group features by reusable technical patterns and player-facing coherence.
Require at least one feature per claimed category. Record source evidence only
in the analysis wave; expose opaque intent IDs and clean-room contracts to the
production wave.

For the compiler baseline, use:

```bash
mccompiler prepare-reconstruction-wave \
  --project path/to/project \
  --parameters wave.json \
  --expected-revision REVISION \
  --json
```

Treat `PENDING_AUTHORIZED_EVIDENCE` as the honest initial state. Advance a
feature only when its evidence and preceding gates exist.

For a single-feature clean-room pilot, use these bounded checkpoints:

- `AUTHORIZED_FEATURE_PACKAGE_REQUIRED`
- `JAVA_PILOT_CANDIDATE_QUALIFIED`
- `PILOT_READY_FOR_CLEANROOM_PRODUCTION`
- `CANDIDATE_READY_FOR_INDEPENDENT_AUDIT`
- `TRANSLATION_LOOP_PROVEN`
- `TRANSLATION_LOOP_PROVEN_WITH_LIMITATIONS`

Never create the production lane before product selection, oracle freeze, and
contract sanitization. Never implement during a readiness-only task.

Use `TRANSLATION_LOOP_PROVEN_WITH_LIMITATIONS` only for explicit non-material
client or harness boundaries. It must not hide rights, isolation, lineage,
semantic, originality, deterministic-build, or Stable-BDS failures.

Missing actual-process launch receipts, any production or repair process that
ran outside the frozen boundary, or an auditor finding that copying prevention
was not technically enforced requires `CLEANROOM_BOUNDARY_FAILED` or
`ISOLATION_NOT_PROVEN`. A later sandboxed rebuild of already-authored code and
assets proves deterministic execution only; it cannot retroactively prove
isolated authorship.

For connected segments, use:

- `SEGMENT_TRANSLATION_LOOP_PROVEN_WITH_LIMITATIONS`
- `JAVA_TO_BEDROCK_PIPELINE_PROVEN_AT_SEGMENT_SCALE_WITH_PLATFORM_LIMITATIONS`
- `REAL_JAVA_MOD_SUBSYSTEM_RECONSTRUCTION_PROVEN_WITH_PLATFORM_LIMITATIONS`

Only use them when the frozen private oracle, mutation suite, contamination and
originality review, isolation and lineage review, deterministic rebuild,
Stable BDS, and Preview BDS all pass for the exact candidate. Keep real-client
item delivery, real-player multiplayer/reconnect, Realm, controller,
split-screen, and physical PS4 pending unless separately executed.

## Report evidence narrowly

Use these evidence states:

- `PENDING_AUTHORIZED_EVIDENCE`
- `EVIDENCE_RECORDED`
- `INTENT_DISTILLED`
- `CLEAN_ROOM_CONTRACTED`
- `IMPLEMENTED`
- `STATIC_QUALIFIED`
- `BDS_QUALIFIED`
- `DESKTOP_VERIFIED`
- `PS4_VERIFIED`

Never claim PS4 compatibility before physical PS4 testing. Use “PS4 planning
profile passed” for theoretical budget evidence and “physical PS4 pending”
until the frozen artifact completes Realm delivery, controller-only,
split-screen, multiplayer, persistence, reconnect, and worst-case-scene tests.

## Deliver

Provide:

- Analysis-only evidence and rights records.
- Gameplay Intent IR.
- Consumer-safe clean-room design and reconstruction-wave contracts.
- Behavior, asset, structure, persistence, multiplayer, and cleanup contracts.
- Original BP/RP/Blockbench/script artifacts when implementation is in scope.
- Deterministic package hash and gate-bound receipts.
- A readiness matrix that distinguishes passed, failed, blocked, and untested
  gates.
